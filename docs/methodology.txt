================================================================================
  METODOLOGIA DE BENCHMARKING — sched-bench
  Avaliação do Intel Thread Director (ITD) com patches IPCC de Ricardo Neri
================================================================================

1. OBJETIVO
-----------
Medir o impacto das classes IPCC (Intel Performance and Capability Classification)
propostas por Ricardo Neri para o scheduler Linux em CPUs Intel híbridas. O artigo
investiga se as classes ITD são úteis para o scheduler e aponta imprecisões e
limitações do mecanismo.

Questões centrais:
  - O scheduler coloca tarefas cls2 (vector/SIMD) nos P-cores preferencialmente?
  - As classes ITD reduzem latência de wakeup?
  - Há ganho de throughput ou eficiência energética para workloads cls2?
  - Qual o overhead introduzido no caminho quente do scheduler?


2. PLATAFORMA
-------------
  CPU    : Intel Core i5-1334P (Raptor Lake-P)
  P-cores: 4 (CPU 0–3, Hyper-Threading, ITD ativo)
  E-cores: 8 (CPU 4–11, sem HT, sem ITD)
  Kernel : Linux 7.0.0-rc1 com patches IPCC portados de Ricardo Neri

  Configurações de kernel testadas:
    vanilla       — sem asym_packing, sem IPCC (CFS puro)
    asym_packing  — asym_packing ativo, sem IPCC
    ipcc          — asym_packing + classes IPCC ativas

  O vanilla é o baseline. Todas as comparações usam Δ% = (X − baseline) / baseline.


3. CLASSES IPCC (ITD)
---------------------
O hardware ITD reporta uma classe por thread a cada intervalo de amostragem.
O scheduler adiciona +1 ao valor do hardware, reservando 0 para "não classificado":

  Scheduler  Hardware  Significado
  ---------  --------  --------------------------------------------------
  0          —         Unclassified (tarefa nunca avaliada ou em E-core)
  1          0         Integer/Scalar (aritmética escalar, FP x87/SSE)
  2          1         Vector/SIMD (loops tight, auto-vetorização implícita)
  3          2         Não documentada (observada em workloads popcount/PDEP)

Mapeamento de workloads de benchmark para classes ITD (medido empiricamente
com /proc/PID/sched, campo ipcc, taskset no P-core 0, sibling HT ocioso):

  stress-ng --cpu-method rand48  → classe 2 (vector) — count oscila 1–1000/s
  stress-ng --cpu-method div16   → classe 1 (integer) — count acumula ~2000/s
  schbench (workers + messenger) → classe 0 (unclassified, curtos períodos)

Nota: a estabilidade da classificação difere significativamente entre classes.
Classe 1 é altamente estável (count cresce monotonicamente). Classe 2 é instável
(count reseta periodicamente). Isso tem impacto direto na eficácia do scheduler.

Efeito do sibling HT (testado em laboratório):
  Com ambos os threads lógicos de um P-core ocupados simultaneamente,
  toda classificação cls2 regride para cls1. O ITD mantém contadores por
  core físico, não por thread lógico. Em workloads com HT ativo, a classe 2
  é essencialmente inalcançável.


4. WORKLOADS DE BENCHMARK
--------------------------
Compute (cls2): stress-ng --cpu-method rand48
  Workload PRNG em loop tight, auto-vetorizado pelo compilador.
  Classificado como cls2 de forma consistente quando rodando em P-core isolado.
  Métrica: bogo-ops/s reportado pelo stress-ng (--metrics-brief).

Background (cls1): stress-ng --cpu-method div16
  Divisão inteira de 16 bits em loop. Classificado como cls1 de forma
  ultra-estável (nunca reclassifica).

Latência (cls0): schbench -t 4 -m 2 --runtime 15
  Benchmark de wakeup latency. Cria messenger threads e worker threads que
  dormem e acordam em ciclo. Não recebe classificação IPCC estável.
  Métrica: percentis p50, p90, p99.9 de latência de wakeup (μs).


5. FASES DE BENCHMARK E CENÁRIOS
----------------------------------

5.1 PLACEMENT CORRECTNESS (Fase 1)
  Mede onde o scheduler coloca cada classe de tarefa.
  Método: polling de /proc/PID/stat a cada 100ms durante execução dos workers.
  Métricas:
    cls2_p_residency : % do tempo que workers cls2 passam nos P-cores (CPU 0–3)
    cls1_e_residency : % do tempo que workers cls1 passam nos E-cores (CPU 4–11)

  Cenários:
    only_cls2 : 12 workers rand48  (sem cls1)       — 1 run × 30s
    only_cls1 : 12 workers div16   (sem cls2)        — 1 run × 30s
    mixed     : 4 workers rand48 + 8 workers div16   — 50 runs × 30s
      (match topologia: 4 P-cores + 8 E-cores)

  O cenário mixed tem alta variância e usa 50 runs para análise estatística.
  Os cenários only_* têm baixa variância e são executados uma única vez.

5.2 LATÊNCIA DE WAKEUP — schbench (Fase 2)
  Mede latência de wakeup de tarefas latency-sensitive sob contention.
  50 runs × 15s por cenário.

  Cenários:
    baseline    : schbench sozinho (sem contention)
    vs_bg4      : schbench + 4 workers cls1 (div16)
    vs_bg8      : schbench + 8 workers cls1 (div16)
    vs_c4bg4    : schbench + 4 workers cls2 (rand48) + 4 workers cls1
    vs_c4bg8    : schbench + 4 workers cls2 (rand48) + 8 workers cls1

  Métricas reportadas: p50, p90, p99.9 (μs).

5.3 LATÊNCIA PERIÓDICA — cyclictest (Fase 2)
  Mede latência de wakeup periódico de threads RT (SCHED_FIFO, prioridade 80)
  afixadas nos P-cores. Indicador de overhead no path de wakeup.
  50 runs × 10s por cenário.

  Cenários:
    pcores_idle : sem carga de fundo
    pcores_load : 4 workers cls2 + 8 workers cls1 rodando em paralelo

  Parâmetros: --interval=200μs --distance=0 --affinity=0-3 --priority=80.

5.4 LATÊNCIA IPC — hackbench (Fase 2)
  Mede latência de troca de mensagens entre grupos de tarefas via pipe/socket.
  Proxy de overhead no caminho de wakeup para pares comunicantes.
  50 runs por cenário.

  Cenários:
    alone : 10 grupos, sem contention
    bg8   : 10 grupos + 8 workers cls1 rodando em paralelo

5.5 LATÊNCIA DE CONTEXT SWITCH — perf bench pipe (Fase 2)
  Mede μs/op de 100.000 operações ping-pong entre dois processos via pipe.
  Indicador direto do overhead do scheduler no caminho quente.
  50 runs. LC_ALL=C para consistência de locale.

5.6 THROUGHPUT — bogo-ops/s (Fase 3)
  Mede throughput do workload cls2 (rand48) sob contention de cls1 (div16).
  50 runs × 10s por cenário.

  Cenários:
    c4_alone : 4 workers rand48, sem background
    c4_bg4   : 4 workers rand48 + 4 workers div16
    c4_bg8   : 4 workers rand48 + 8 workers div16 (sistema saturado: 12/12 CPUs)

  Background sobe antes do compute e roda por mais tempo para cobrir a janela.

5.7 EFICIÊNCIA ENERGÉTICA — ops/Joule (Fase 4)
  Mede ops/s e energia do pacote (RAPL) simultaneamente.
  Métrica: compute_ops / pkg_joules (bogo-ops por Joule consumido).
  RAPL via /sys/class/powercap/intel-rapl:0/energy_uj (requer sudo).
  50 runs × 12s por cenário.

  Cenários (espelham throughput para correlação):
    baseline_c4 : 4 workers rand48 sozinhos
    c4_bg4      : 4 workers rand48 + 4 workers div16
    c4_bg8      : 4 workers rand48 + 8 workers div16

5.8 OVERHEAD DO SCHEDULER (Fase 5)
  Mede overhead direto das modificações no scheduler.

  context switches : perf stat -e context-switches -a, 10s × 50 runs
                     Workload: stress-ng --cpu $(nproc) --cpu-method rand48
  cpu migrations   : perf stat -e cpu-migrations -a, 10s × 50 runs
                     Workload: stress-ng --cpu $(nproc) --cpu-method rand48
  pipe latency     : perf bench sched pipe -l 100000, 50 runs (via seção 4)


6. ANÁLISE ESTATÍSTICA
-----------------------
  Todas as comparações usam vanilla como baseline.
  Δ% = (valor_kernel − valor_vanilla) / valor_vanilla × 100

  Significância estatística:
    Teste t de Welch (duas amostras, variâncias desiguais)
    *** p < 0.001   ** p < 0.01   * p < 0.05   ns = não significativo

  Para placement (mixed, 50 runs): t-test aplicado separadamente para
  cls2_p_residency e cls1_e_residency, relatando ΔP% e ΔE% com significância.

  Tamanho de amostra: 50 runs por cenário. Justificativa: para os efeitos
  observados (Cohen's d > 0.5 nas métricas principais), 50 amostras fornecem
  potência estatística > 80% com α = 0.05.


7. REPRODUTIBILIDADE
---------------------
  Scripts: https://github.com/[repo]/sched-bench
  Dependências: schbench, cyclictest, stress-ng, perf, Python 3 (scipy, numpy,
                matplotlib, pandas)
  Setup: ./setup_deps.sh  (detecta Arch Linux ou Debian/Ubuntu)
  Execução: sudo ./run_battery.sh --kernel <tag> --runs 50
  Análise: python3 analysis/compare.py --kernels vanilla,asym_packing,ipcc

  Cada fase tem skip logic: se os arquivos de resultado já existem com RUNS
  amostras, o benchmark é pulado. Execuções interrompidas podem ser retomadas.

  LC_ALL=C é forçado antes de todos os comandos perf para garantir consistência
  do separador decimal independente do locale do sistema.


8. LIMITAÇÕES CONHECIDAS
--------------------------
  - Hyper-Threading ativo durante todos os testes. Com HT ativo, cls2 regride
    para cls1 sempre que o sibling está ocupado (verificado empiricamente).
    Isso limita a observabilidade do efeito IPCC em condições realistas.

  - O workload rand48 (cls2) tem count instável (oscila entre 1 e ~1000 a cada
    segundo), enquanto div16 (cls1) tem count monotonicamente crescente. A
    instabilidade de cls2 pode impedir o scheduler de agir com confiança.

  - schbench opera em classe 0 (unclassified). Testes de latência medem o
    comportamento do scheduler para tarefas sem classe ITD definida.

  - RAPL mede energia do pacote inteiro (P-cores + E-cores + uncore). Não é
    possível isolar energia apenas dos P-cores ou E-cores individualmente.

  - Os patches IPCC foram portados manualmente para kernel 7.0.0-rc1. Pode
    haver divergências menores em relação à versão original de Ricardo Neri.
